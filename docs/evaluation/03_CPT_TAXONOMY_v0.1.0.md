# CPT and Taxonomy Inventory — v0.1.0

**Task:** VGN-55, bounded research inventory of effective WordPress post-type and taxonomy registrations, source authority, taxonomy terms and aggregate relationships.

**Runtime target:** `vgnova-local-10039`, `http://localhost:10039` (LocalWP site ID `nAZNpFs99`).

**Inspection date:** 2026-11-19.

**Source baseline:** branch `main`, HEAD and `origin/main` both `454346d9e6a2c36864a4bbd944e52596f16e09c1` at inspection. This file is a research artifact and is not yet committed.

## 1. Executive Summary

The effective WordPress runtime registry exposed **63 post types and 55 taxonomies**. The local read-only database snapshot contained **394 terms attached to registered taxonomies**, plus **8 term rows under three unregistered taxonomy keys**. Aggregate counts cover 873 `wp_posts` rows across 47 type/status groups; they do not count WooCommerce HPOS tables or other plugin-owned tables.

The principal domain findings are:

- `content_topic` is registered by source-controlled Platform Core, is hierarchical/public/REST-enabled, supports eight content types and has 55 terms in seven roots. One published post relationship exists in the current runtime. That differs from the architecture register’s post-QA statement of zero relationships.
- `content_category` remains an active, public, hierarchical ACF taxonomy on ten object types. It has 13 terms and zero current relationships, but the legacy register documents live Bricks, FluentSnippets, Featured Content Manager, partner-mapping and HappyFiles consumers. Zero assignments do not satisfy its removal gate.
- Core `category` remains registered but has no registered object types. One term relationship still points to one published post while its stored term count is zero.
- `person` and `medewerker` coexist as public profile CPTs at `/mense/` and `/medewerkers/`. Their migration boundary remains separately gated.
- The current effective competition-entry key is `kompetisie_entry` with the single-item rewrite `/inskrywing/`. The supplied project inventory also uses `kompetisie_inskrywing`; that key was not registered.
- Two active Voelgoed Live taxonomy generations coexist: `broadcast_series`/`broadcast_type` and `uitsending_series`/`uitsending_type`. Both have terms; the series/type usage and rewrite slugs differ.
- Database storage contains four unregistered post-type keys and three unregistered taxonomy keys. These are reported as residues, not deletion candidates.

## 2. Inspection Scope and Evidence

### Inspected

- Read the complete [coordination brief](COORDINATION_BRIEF_v0.1.0.md), repository instructions supplied with the task, and the current source baseline.
- Read-only WordPress abilities `acf-check-setup`, `acf-list-post-types`, `acf-get-post-type`, `acf-list-taxonomies`, and `acf-get-taxonomy` checked the active ACF Pro setup and its CPT/taxonomy definitions. The runtime reported WordPress 7.1.5, PHP 8.5.12 and ACF Pro 6.8.1.
- A read-only `execute-php` registry query captured registration properties for every post type and taxonomy using `get_post_types()`, `get_taxonomies()`, `get_all_post_type_supports()` and `get_object_taxonomies()`, with registration flags, rewrite, capabilities, supports and attached taxonomy names.
- The exact shell guard for direct database reads was `flock -n /tmp/vgnova-evaluation-read.lock php <<'PHP'` (with the query script supplied on stdin). Its PDO statements grouped `wp_posts` by `post_type, post_status`, selected taxonomy/term IDs, names, slugs, parents and stored counts, and grouped `term_relationships` by taxonomy and term. The observed results were 873 post rows in 47 status groups, 394 terms for registered taxonomies plus 8 residue terms, and 40 non-zero taxonomy/term relationship groups. No object IDs, user records, order details, customer fields, or entity content were selected.
- Compared all eight active ACF JSON files listed below with the source-controlled files; all eight file contents matched byte-for-byte. Compared the runtime plugin copy of `ContentTopicTaxonomy.php` with the source-controlled file; they matched.

### Read-only limits and caveats

- The general-purpose PHP inspection ability is marked as capable of writes. The submitted code was reviewed and only read registry objects; a first extraction requested a taxonomy property that does not exist and emitted warnings. The query was corrected and rerun successfully. No mutation was requested or issued.
- WP-CLI’s `wp db query` path could not run because the local client lacked the `mysql` executable. The direct PDO reads above were the read-only fallback; the database client error was `env: 'mysql': No such file or directory`.
- WordPress bootstrap/plugin hooks may run during the runtime registry call. Incidental bootstrap effects were not observable from these reads; `INCIDENTAL_BOOTSTRAP_SIDE_EFFECTS=UNKNOWN`.
- The Bricks template scan counted taxonomy-key tokens in stored template fields. It is a structural clue, not a rendered-behavior test; serialized/dynamic settings can reference IDs or indirect query logic without containing a taxonomy slug.
- Runtime-only FluentSnippets bodies were not available in the repository. Named snippet consumers below are documented by the current legacy register; their current runtime code bodies were not independently read.
- The counts below are aggregate `wp_posts` data. WooCommerce HPOS tables, user records, external plugin tables, traffic, and media contents were not inspected.

### 3.3 Full term hierarchy and IDs

Each stored registered term is listed as `#term_id Name [slug; parent; stored_count]`. ## 4. Current Architecture and Configuration

### Registration authority

- **WordPress core** owns the core post types and core taxonomies. Core `category` is registered with `object_type=[]` in the effective registry; `post` has no attached `category` entry.
- **ACF Pro** is the active registration authority for ten project CPTs and fifteen project taxonomies. Runtime ACF reports 10 active custom post-type definitions and 15 active custom-taxonomy definitions; some definitions are stored in ACF data and eight have matching source JSON.
- **Voelgoed Platform Core** owns the canonical `content_topic` taxonomy. The source declares exactly `post`, `mto-course`, `product`, `tc_events`, `medewerker`, `uitsending`, `kompetisie`, and `person` as object types and uses rewrite slug `onderwerp`. See [ContentTopicTaxonomy.php](../../site-code/voelgoed-platform-core/includes/Taxonomy/ContentTopicTaxonomy.php#L16).
- **Specialist plugins** own their domain registrations: Tickera’s `tc_events` and ticket/order types; Masteriyo’s `mto-*`; WooCommerce’s product/order types and `product_*`; PMPro’s user taxonomy; Bricks’ template types/taxonomies; HappyFiles folder taxonomies; and Voelgoed Member Perks’ `vg_perk` model. These attributions follow the effective names/labels and active plugin list; exact third-party source revisions were not audited.
- ACF custom CPTs use `capability_type=post` and `map_meta_cap=true` in the effective registry unless shown otherwise in the table. Specialist plugin CPTs use their plugin capability types (for example `tc_event`, `course`, `product`, and `vg_perk`). Registered capability strings are not evidence that editor roles have the intended grants.

### Canonical and legacy classification

- `content_topic` is the seven-root semantic subject tree; its hierarchy is source-controlled in Platform Core and its terms are set up only by an explicit CLI command, not by ordinary page requests. The Platform Core source also says rewrite flushing is kept out of normal requests.
- `content_category` is a distinct current legacy taxonomy. It mixes the legacy semantic roots with the Leefstyl commercial branch. It must not be treated as a replacement name for `content_topic`. The legacy register says keep it until term-by-term mapping and every consumer pass the migration gate.
- `editorial_format` and `editorial_collection` are private, post-only ACF taxonomies; they are not registered for any other content type.
- Commercial `Leefstyl` children remain terms of `content_category`; they are not part of the seven canonical topic roots.

### Person, event and product relationships

- `person` is the canonical public profile CPT at `/mense/`; `medewerker` remains the live legacy profile CPT at `/medewerkers/`. The runtime has one published `person` row and five published `medewerker` rows. No profile names or IDs are included.

## 5. How It Works

1. WordPress bootstraps core and active plugins; ACF registers its database/JSON-backed definitions, plugins register their own entities, and Platform Core registers `content_topic`. The effective registry is the runtime truth for this snapshot.
2. Post rows are persisted in `wp_posts`; taxonomy vocabularies and their object links are stored in the WordPress term tables. The aggregate query counted current status values without selecting post titles or identifiers.
3. ACF JSON definitions are version-controlled inputs for the eight matched definitions. The ACF API’s list and detail operations disagree on the `source` label for those eight, so the byte match and effective runtime state are stronger evidence than that label alone; its precise semantics remain unresolved.
4. `content_topic` source declares a fixed 55-term definition and a registration guard. The source requires explicit setup for seed terms and avoids automatic rewrite flushing on normal requests. One current runtime relationship exists despite prior architecture notes saying zero after QA.
5. Bricks consumes these entities through templates, query conditions, dynamic data and the Platform Core adapter. Template existence and stored taxonomy-key tokens were read; actual rendered results, access behavior and responsive states were not exercised.
6. First-class relationship records for events and product contributions are separate post types, consistent with the richer domain model. Existing simpler taxonomy and ACF relationships remain independently governed.
